# fluidsim — real-time particle-based fluid simulation

An SPH (smoothed particle hydrodynamics) fluid solver with an OpenGL/GLUT viewer,
written for a diploma thesis at TU München in 2004/2005 and still running.
The solver is `fluid.h`, a single header; `main.cpp` is the viewer and the scene.

- the thesis: **[thesis/Diplomarbeit.pdf](thesis/Diplomarbeit.pdf)** —
  *Partikelbasierte Fluidsimulation für interaktive Anwendungen*, Leo Wandersleb,
  TU München, submitted 2005-01-17
  ([as a web page](https://giszmo.github.io/fluidsim/thesis/Diplomarbeit/), German)
- its LaTeX sources and figures: `thesis/`
- the code as it was when the thesis was handed in: tag
  [`thesis-2005-01-17`](https://github.com/Giszmo/fluidsim/releases/tag/thesis-2005-01-17)

## The idea

Neighbour search without a grid. Each particle stores an implicit **cell ID** and the
particles are kept **sorted by it**, so nothing is allocated per cell and memory scales
with the particle count rather than with the size of the domain. The cell ID is taken
modulo the ID space, which makes the domain effectively unbounded; the collisions that
introduces are resolved by the distance test SPH performs anyway. Adjacency along x
comes free from the sort order, so 3D needs four sorted lists rather than the eight
shifted grids of the half-cell-offset trick. The thesis reports domains of (100 000)³
cells at 3 000 particles in under 15 MB.

It holds up. Cost per particle is flat from 3 000 to 800 000 particles (below), which
is the claim the thesis makes and the reason there is no size at which this design
falls over.

## Building

Needs a C++ compiler with OpenMP, GLUT and OpenGL. On Debian/Ubuntu:

```sh
apt install build-essential freeglut3-dev
make            # -> main.$(uname -s).$(major)_std   (debug, -g)
make opt        # -> main.$(uname -s).$(major)_opt   (-O3 -march=native)
make opt ARCH=x86-64-v2   # for a binary that has to run on another machine
```

Verified on Debian forky, GCC 15.3.0, freeglut 3.4.0 — no source changes needed.
`make` also still honours the `dbg` and IRIX branches inherited from the TUM course
makefile. There is no Boost dependency any more.

## Running

```sh
./main.Linux.7_opt                 # the scene as it has always been: 1875 particles
./main.Linux.7_opt -n 100000 -r    # 100 000 of them, and start running
./main.Linux.7_opt --help
```

|---|---|
| `-n N` | how much liquid to drop, in particles (default 1875). The scene is one tetrahedron and this scales it |
| `-t N` | OpenMP threads for the solver (default: as many as the machine has) |
| `-r` | start running instead of paused |
| `-s` | start with the marching-cubes surface on |

### The default scene

A `sink`-shaped ground height field, a 4×4 plate at z=0 that sets the speed of any
particle crossing it to +70 (so the fluid is thrown back up), and two tetrahedra of
liquid dropped from above. **All the barrier, teleport and extra set-speed geometry in
`main()` is commented out**, so the default scene contains no walls — worth knowing
before concluding that barrier collision does not work.

## The simulation is not tied to the frame rate

It used to be. `DisplayMain()` was both the display callback and the idle callback, and
it called `progress()` once, so the program took exactly one simulation step per drawn
frame — and `glutSwapBuffers()` blocks until the next vertical retrace. On an ordinary
screen that is 60 steps a second whatever the machine could have done, and on a slow
frame it is fewer.

The solver runs in a thread of its own now (`simthread.cpp`) and steps as fast as it
can. It publishes a **snapshot** — the particle positions, and the marching-cubes
surface when the viewer is drawing one — whenever the renderer asks for the next one,
and only then, so the mesh is built once per drawn frame rather than once per step.
Three snapshots rotate between the two threads, so neither waits for the other: the
solver fills one while the renderer draws another. Everything that touches the `Fluid`
happens on the solver thread; the renderer only ever reads a published snapshot, which
nothing writes to while it holds it.

What that is worth, 20 000 particles with the surface on, software-rendered on this
20-core box, `-t 8`, measured from the per-second line:

| | steps/s | frames/s |
|---|---|---|
| the previous build, one step per frame | 55 | 55 |
| the solver on its own thread | **530–900** | 6–12 |

The frame rate falls because the two now compete for the same cores *and* because the
fluid gets ten times as far in the same wall second, so there is ten times as much
surface to draw. On a machine with a real GPU the renderer costs almost no CPU and that
trade does not arise.

Two consequences worth knowing:

- **The water moves faster in wall-clock time**, because a step is still dt=0.004 of
  simulated time and there are now many more of them per second. `-H N` caps the step
  rate; at the default dt, `-H 250` is exactly real time, and `-H 60` is what a 60Hz
  screen used to impose.
- **`-t` applies to the solver thread.** OpenMP's thread count is a property of the
  thread that enters the parallel region, not of the program, so it is set from inside
  the solver thread; `OMP_NUM_THREADS` works as before.

## How fast the solver itself is

The honest unit is **simulation steps per second**: 25–30 of them is what "smooth"
meant in 2005, and still does.

Headless, a dense block of liquid (the worst case — every particle has a full
neighbourhood), AMD Ryzen 9 7900X, best of three:

| moving particles | 2005 code, 2004 build flags, 1 core | today, `-march=native`, 20 threads |
|---|---|---|
| 3 414 | 301 steps/s | — |
| 18 295 | 50 steps/s | **525 steps/s** |
| 98 046 | 9.3 steps/s | **94 steps/s** |
| 198 647 | 4.5 steps/s | **45 steps/s** |
| 395 563 | — | 22 steps/s |
| 833 646 | — | 9.6 steps/s |

Two independent factors, both measured on the same bench:

- **build flags, ×1.4.** The `opt` flags were written for a Pentium 4 and turned SSE2
  off (`-march=x86-64 -mno-sse2 -msse -mfpmath=sse,387`). Just `-march=native` is
  9.3 → 13.0 steps/s at 98k.
- **cores, ×6.6.** At 98 046 particles: 13.3 steps/s on one thread, 26.0 on two, 49.4
  on four, 76.9 on eight, 86.5 on twelve, 87.5 on twenty. It stops scaling at about
  eight because it becomes memory-bound, not because of a lock — there is none.

Cost per particle per step stays at roughly 0.11 µs from 18k to 833k.

## How the parallelism works

`progress()` is four phases, and each of them is now spread over every core.

The two neighbour passes — density and force — are 71 % of the time and are the
interesting ones, because both write to **both** particles of a pair. Each thread
accumulates into its own force and density buffer and the buffers are summed
afterwards, so the passes need no synchronisation at all. Thread 0's force buffer
starts at the global acceleration, which makes the sum over all buffers exactly what
the serial pass used to accumulate on top of it: built without `-fopenmp`, or run with
`OMP_NUM_THREADS=1`, the solver reproduces its pre-2026 results bit for bit.

Boundary, teleport, shift and setspeed corrections move the *scanning* particle. They
go to a working copy that is written back after the pass, so no thread writes a
position another thread is reading, while within one particle's own scan they still
compose exactly as they did — that is what keeps a particle resting on a barrier from
being pushed out once per barrier sample.

`sortparticlelists()` sorts the four lists in parallel with `std::sort`. The four lists
are independent by construction, which is the sorted-list design paying off a second
time; the keys are unique, so the order is total and the result does not depend on how
the work is split. Four `boost::thread`s running a hand-written `quickbubblesort` used
to do this, which is what the 2008/2009 rework had added; it was worth about 6 %.
`quickbubblesort` is still in the file, unused, because it is part of what the thesis
describes.

## Regression check

```sh
make check
```

`test/headless.cpp` runs the solver without a window and prints an FNV-1a checksum over
every particle position, so two builds can be compared bit for bit. Scenario 0 drops
liquid on the centre of a square plate (it comes to rest on it); scenario 1 drops it
beside the plate (it falls straight past). `./test/headless cmp` additionally runs an
18 296-particle scenario on one thread and on all of them and compares the end states:
worst displacement 1.9e-06 against a particle diameter of 1.0, i.e. float rounding.

## The surface

`c`, or `-s`, turns on the marching-cubes surface. It produced nothing at all until
2026, for four separate reasons, and they are worth listing because each one hid the
next:

1. **Nine of twelve edges never got a vertex.** `autogenerated.h` only ever assigns
   `vn_id[pxpy]`, `vn_id[pxpz]` and `vn_id[pypz]` — the three edges at a cube's +++
   corner. The other nine belong to neighbouring cubes, and the code that was to copy
   them across never made it out of the commented block in `fluid.h` into the generated
   switch. Every triangle that referenced one of the nine was dropped by the guard in
   `get_surfacegrid`, which is to say almost all of them.
2. **The same cube was triangulated up to eight times.** `create_cubes()` makes, for
   every occupied cell, the eight cubes that have it as a corner, so each copy knows
   about one corner and no copy knows about all of them. Nothing merged them.
3. **Every grow of the node list lost its newest node.** Nodes live at indices
   `1..count`, which is `count+1` entries, and `resize_node_list` was asked to copy
   `count`. The lost node read back as zeroed — a cell at the origin holding no
   particles — and dragged a spike of surface to (0,0,0).
4. **OpenGL read every index as two.** The triangle indices were `unsigned long`, four
   bytes on the Windows this was written on and eight here, handed to `glDrawElements`
   as `GL_UNSIGNED_INT`. So even after the first three, what came out was garbage
   geometry across the whole screen.

Three more went with the spike that was still left in 2026 — a triangle reaching right
across the domain, every few seconds:

5. **A particle that leaves the box comes back as a cell in the middle of the pool.**
   The jet throws a few particles hard enough to clear the top of the domain. The cell
   index computed for one of them then overflows its bit field: x spills into the y
   field, y into z, and z is masked off again by `_BoxIdBitmask`. A particle 500 m
   overhead is filed under a cell in the middle of the fluid, collides with what is
   there, and is thrown further out. `cell*2bitplus()` saturates now. The y and z fields
   overflowed on their own even for a particle *inside* the box, because the staggered
   lists ask for `(i+2)>>2` as well as `i>>2` and the field holds exactly one of them.
6. **A cell's representative point was not always inside the cell.** The sort is one
   step old by the time the surface is built, so a fast particle is averaged into the
   cell it has just left. Vertices are placed relative to that point, so it dragged
   triangles after it. `fill_node_list()` clips it into its own cell.
7. **The last cell of a row built a cube out of both ends of the domain.** Its +1
   neighbour does not exist, and the index that names it carries into the next bit
   field, so cell `(cellsx-1,y,z)` and cell `(0,y+1,z)` come out exactly `_dx` apart.
   `create_cubes()` does not create those cubes.

`make_vertices_for_cubes()` replaces the generated stage: one vertex per crossed edge,
all twelve, placed on the filled cell and stepped towards the empty one by as much of a
cell as its particles fill — the 2005 rule, which used to be a 200-entry table of
`min(cbrt(n/40), 0.99)`. Cubes that share an edge compute bit-identical coordinates for
it, because they compute it from the same cell, so a map welds them into one indexed
mesh and normals are accumulated per face for smooth shading.

`test/surface`, part of `make check`, runs the viewer's own scene for 900 steps and
asserts every step that no triangle is longer than a cube (two corners of one cube are
at most `2*sqrt(3)*cellsize` apart), that every index points at a vertex that exists,
and that triangles come to about twice the vertices, which is what a closed
triangulated surface gives. At 100 000 particles over 1 500 steps the longest edge is
**5.99** against that bound of 6.93; before the three fixes above it was **4114**. The old generator and its 4 000 lines of
`autogenerated.h` are still in the tree; they are what the thesis describes.

## Round water: TRUFORM, and what replaced it

The 2005 program asked the card for `GL_PN_TRIANGLES_ATI` — ATI's TRUFORM. You handed
it an ordinary triangle with a normal at each corner, it built a cubic Bézier patch for
the positions and a quadratic one for the normals, subdivided, and gave you a curved
surface for one `glEnable`. That is close to ideal for water made of blobs: the mesh a
marching-cubes pass produces is coarse by construction, but its normals are good,
because they come from the density field rather than from the triangles.

The extension is gone. It was ATI-only, and AMD dropped it too; no current driver
exposes it. Its descendant is the tessellation stage of OpenGL 4.0 (2010), which every
GPU built since about then has. The maths is the same — it is Vlachos, Peters, Boyd and
Mitchell, *Curved PN Triangles*, I3D 2001 — but the patch is now evaluated by shaders
you write, and `shaders.cpp` is those shaders.

What that buys over the fixed-function version:

- **The subdivision level is per edge, and chosen here from how long the edge comes out
  on screen.** Water close to the camera is smooth; spray in the distance stays at one
  segment and costs nothing. TRUFORM had one global level.
- **Shading is per pixel.** The fixed-function path lights each vertex and interpolates
  the colour, so a specular highlight lands on a vertex or is lost. The evaluation
  shader hands the fragment stage a normal per generated vertex and the lighting is done
  there.

And what it costs: a shared edge has to be subdivided identically from both sides or the
seam cracks, which TRUFORM guaranteed for you. Here it falls out of the construction —
both the level and the curve of an edge are computed from that edge's two endpoints and
nothing else, so the two triangles sitting on it cannot disagree.

The shaders are `#version 400 compatibility` on purpose: they read
`gl_ModelViewProjectionMatrix`, `gl_LightSource[]` and `gl_FrontMaterial`, so the camera,
the two lights and the material stay where the rest of the program puts them and a
tessellated frame is comparable with an untessellated one. `t` toggles between them.

On a driver without OpenGL 4 tessellation the program says so once on stdout and draws
plain triangles; nothing else changes.

## The other way to draw it: screen-space fluid

`-S`, or the `S` key, throws the mesh away. The particles are splatted into a
depth buffer as spheres, the depth buffer is smoothed, and the surface is shaded from
the normals of the smoothed depth — van der Laan, Green and Sainz, *Screen Space Fluid
Rendering with Curvature Flow*, I3D 2009, with a bilateral blur where they used
curvature flow. It is what the real-time fluid renderers do, FleX and PhysX among them.

Four passes, all in `shaders.cpp`:

1. every particle as a sphere, writing its eye-space z and a real depth, so spheres
   intersect each other instead of being flat discs;
2. every particle again, additively and with no depth test, for how much water is in
   front of each pixel — that is what makes thin spray pale and a deep pool dark;
3. the depth, blurred. The filter radius is the splat's own projected size,
   recomputed per pixel from the depth that is there, so the filter is the same size in
   *world* units at every distance. A fixed pixel radius smears the far water into a
   sheet and barely touches the near water;
4. one full-screen triangle: rebuild the eye position from the smoothed depth, take the
   normal from its screen derivatives, light it, write depth so the water sits properly
   in the scene.

**The offscreen buffers are scaled to the zoom.** Everything here is per pixel — the
splats, the blur, the shading — so at a fixed buffer size the whole thing gets more
expensive the closer the camera is, while the blur, which has to be capped somewhere or
it costs a texture read per pixel per step of its radius, smooths relatively *less and
less*. Zoomed in you paid the most and saw individual spheres. The buffers are sized
instead from how big a splat comes out at the camera's distance, so a splat comes out about
six pixels across in them and both the cost and the amount of smoothing stay put.
It is the one change that fixes the look and the frame rate at the same time. It stops
at half the window in each axis, because below that the silhouette starts showing the
buffer's own pixels and single droplets of spray fall between them — so from very close
up the cap is still the cap.

Two things worth knowing about it.

**The water is composited last.** It is transparent, so it has to be drawn after the
rest of the frame; drawn where the particle dots used to be, it blends against the
cleared background and comes out black.

**It is lit by a sky, not only by the scene's two lamps.** Water absorbs red first, and
the only lamp facing the camera in this scene is the red one, so deep water shaded from
those two lights alone goes black. The composite adds a hemisphere ambient — pale blue
from world +z, dark from below — which is what actually lights water outdoors. And it
honours `l` like everything else in the viewer does: the scene's two lamps are a
saturated red one and a saturated blue one, which on a smooth surface read as two-tone
plastic rather than as water, and lighting is off by default. With it off the water is
lit by the sky alone.

What it gives you: no marching cubes pass, no mesh to rebuild and re-upload every frame,
and a cost that is per pixel rather than per particle. What it cannot give you is
geometry — no reflections off the water, no shadow casting, nothing to export. That is
what the tessellated marching-cubes path is for.

### What each way costs

One frozen frame, 30 014 particles, 1024×768, on a machine with **no GPU at all** — Mesa's
llvmpipe rasterises in software, so every pixel below is CPU work and a real GPU
reorders this completely. The marching-cubes rows include rebuilding the mesh on the CPU
every frame, which is the cost screen-space does not pay.

| | frames/s |
|---|---|
| nothing drawn | 2090 |
| marching cubes, flat triangles | 351 |
| marching cubes + PN tessellation | 130 |
| screen-space fluid | 60 |

The screen-space row is from before the offscreen buffers were scaled to the zoom, and
it is a single camera position, which for that path is the thing that matters most. What
the scaling is worth, on the frozen opening frame at 10 000 particles, 1024×768, by how
far the camera is from the water:

| camera | before | after |
|---|---|---|
| close enough that the water fills the window | 28 fps | **103** |
| a little further | 61 | 99 |
| the whole splash in view | 131 | 177 |
| far | 151 | 204 |

And the cost really is per pixel and not per particle: on the closest of those, 2 000
particles gives 104 fps, 10 000 gives 103 and 40 000 gives 110.

## Fixed here

**Out-of-bounds read in the neighbour scan.** The four scan loops in
`collidewithneighbours` and `collidewithneighboursforrho` read `_sortlist[...]` *before*
the `sortlistindex < _particlecount` bounds check. `&&` evaluates left to right, so every
scan read one slot past the populated region and decided whether to keep walking on
whatever was in it. `_sortlist` was never initialised, so that slot was heap garbage.
The backward loops were worse: `sortlistindex` starts at `startsortlistid - sortlistbase
- 1`, which underflows to 2^64−1 when the particle is first in its list, so the read
landed in the previous list's memory. The `//TODO: workaround??` guard in `condcollide`
(`( first < second ) & ( second < _particlecount )`) exists to throw away the bogus
particle ids this produced — it is why the simulation worked at all.

The fix swaps the two operands of `&&` in all four loops so the bounds check runs first,
and value-initialises `_sortlist`. Valgrind, scenarios 0 and 1, 0.8 s of simulated time:
391 and 383 errors from 4 contexts before, **0 from 0 contexts** after.

It is behaviour-neutral on Linux — because fresh pages from the kernel are zeroed, so
the garbage reads as zero and the `condcollide` guard drops it. On the MSVC heap the
code was originally written against, it would not have been zero.

**One phantom particle per drop of liquid.** Moving particles live at the front of the
array and control particles behind them, so adding a moving particle moves the control
particle that is in the way to the end — and `newparticle()` counted that move as a new
particle as well as counting the new one. The default scene reported "3760 particles,
1875 moving" when it holds 1875 liquid and 10 control particles; half the capacity went
to uninitialised particles sitting at the origin, in one cell, which is exactly where
the jet is. They had no physical effect — their kind is `undefined`, so `collide()`
falls through — but every neighbour scan that reached that cell walked all of them, and
asking for 100 000 particles overran the 150 000 capacity and hung before the first
frame. Behaviour-neutral to fix: the `make check` checksums did not move.

**Linking with GCC.** The makefile drives the compiler as `gcc`, which no longer pulls in
`libstdc++`; it is `g++` now. That is the only source-level change the 2009 code needed
to build on a current toolchain.

## Known rough edges

- `fluid.h` is MSVC-flavoured C++ from 2005: `unsigned __int64` throughout, and the whole
  solver in one 3 000-line header. `bicubic_bezier_patch.h` has no include guard.
- The makefile is the 2004 TUM course template with CRLF line endings and `-L` paths for
  IRIX and XFree86 that have not existed for twenty years.
- In the BOUNDARY branch of `collide()`, `float d = r.abs()` is computed and never used;
  the repulsion feeds the signed plane distance into `w_poly6_grad()`, which expects a
  radial distance. Harmless for the boxed barrier patches the code actually builds, but
  it is a loose end.
- The pressure force divides by the *neighbour's* density only and is then applied
  symmetrically. That is Müller 2003 plus Newton's third law, which is a defensible
  choice and the reason the pair has to be evaluated from one side; it is not a bug, but
  it is the thing to know before rewriting the force loop.
- A particle that hits a `teleport` or `shift` patch stops accumulating force for that
  step. That was true before the parallel work too.
